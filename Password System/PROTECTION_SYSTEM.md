# Portfolio project protection system

Last reviewed: 2026-08-26

This document records how the portfolio's password protection was designed so
that the authentication system can be reconnected after future page or folder
reorganizations.

## 1. Architecture summary

The protection system is server-side. The browser never compares the password,
stores the password, or receives protected project content before
authentication.

The flow is:

```text
Request project page
        |
        v
Read project configuration
        |
        +-- public project --------------------> render page
        |
        +-- protected + valid session ----------> render page
        |
        +-- protected + no valid session -------> password page / 404 gate
                                                   |
                                                   v
                                          POST password to server
                                                   |
                                  scrypt hash verification succeeds
                                                   |
                                                   v
                                  signed 7-day session cookie
```

The same session is shared by all protected projects. It is not a separate
password per project.

## 2. Source of truth for project access

`Password System/config/projects.data.json` contains one record per project:

```json
{
  "project-slug": {
    "title": "Project title",
    "source": "projects/category/project.html",
    "protected": true
  }
}
```

- `protected: false` means the project can be opened directly.
- `protected: true` means the page and its case-study media require the shared
  portfolio password.
- `source` must point to the page source used by the current site architecture.

`Password System/config/projects.config.ts` is the server-only typed reader.
Normally, changing a project's access should require editing only the JSON
file.

In the last committed version (`90681ef`), the protected projects were:

- `glamhub`
- `armani-beauty`
- `louis-vuitton-bugatti`

During the current website rebuild, the project list has been reconnected to
the Backup case studies and all registered projects are intentionally public.
This keeps the protection mechanism dormant while the page architecture is
being finalized.

## 3. Authentication components

### Password verification

`Password System/auth/password.ts` verifies the submitted password on the
server.

- Preferred variable: `PORTFOLIO_PASSWORD_HASH`.
- Hash format generated by `pnpm auth:hash -- "your password"`:
  `scrypt:<salt>:<hash>`.
- The code also accepts the earlier `$` separator format for compatibility with
  existing Vercel environment variables.
- A plain `PORTFOLIO_PASSWORD` fallback exists for simple legacy deployments,
  but the hashed variable is preferred.

Never put the real password or hash directly into HTML, JavaScript, project
pages, or public assets.

### Session cookie

`Password System/auth/session.ts` creates and verifies a signed session token.

- HMAC-SHA256 signature using `SESSION_SECRET`.
- `SESSION_SECRET` must be at least 32 characters.
- Session lifetime: 7 days.
- Token includes `AUTH_VERSION`; increasing this value invalidates all existing
  sessions.
- Production cookie: `__Host-portfolio_session`.
- Local cookie: `portfolio_session`.
- Cookie flags: `HttpOnly`, `Secure` in production, `SameSite=Lax`, site-wide
  path `/`, and high priority.

### Page route

`app/[[...path]]/route.ts` resolves both the current `/work/<slug>` style route
and legacy project URL forms, depending on the active page architecture.

- `GET` checks the project configuration and session.
- `POST` accepts the password form, verifies same-origin requests, validates the
  password, and sets the session cookie.
- Protected responses are dynamic and are never publicly cached.

The password page implementation used by the last committed version was:

- `Password System/auth/password-page.html`
- `Password System/auth/password-page.ts`

The password-entry files are retained in the current rebuild and remain
connected to the same `POST` route. The current project configuration marks all
registered projects as public, so this gate is dormant until a project is
changed to `protected: true`.

## 4. Protected project media

Case-study images, videos, PDFs, and other project-only assets must not be
served directly from the public static directory.

### URL rewriting

When a project page is rendered, project media URLs are rewritten to:

```text
/project-assets/<project-slug>/static/<asset-path>
```

Shared infrastructure such as CSS, JavaScript, fonts, and brand assets can
remain under `/static/`.

### Asset gateway

`app/project-assets/[project]/[...asset]/route.ts`:

1. Looks up the project slug.
2. Rejects unknown projects and unsafe path segments.
3. Requires a valid session when the project is protected.
4. In Vercel, reads from Private Blob with `access: "private"`.
5. In local development, reads from the editable `Assets/` directory.
6. Supports byte ranges for video playback.

Protected asset responses return `404` when unauthorized and use private,
no-store cache headers.

### Blob storage

`pnpm assets:upload-all` runs `scripts/upload-project-assets.mjs`. It scans the
configured project pages, uploads referenced project media to the private Blob
library, and keeps shared public assets out of the private upload set.

The deployed route and upload script must agree on the Blob key prefix. The
existing design uses keys under:

```text
library/static/<asset-path>
```

Do not make the Blob store public just to simplify rendering.

## 5. Public asset preparation

`scripts/prepare-public-assets.mjs` generates `public/static/` before `dev` and
`build`.

- `Assets/` is the editable source library.
- `public/static/` is generated and ignored by Git.
- Shared CSS, JavaScript, fonts, and brand files remain public.
- Project-only files are excluded from the public copy when they are not also
  needed by a public page.

If page folders or HTML sources change, update the project configuration and
the asset URL rewriting rules together. A page can be protected correctly while
still leaking media if its `<img>`, `<video>`, CSS, or JavaScript URLs bypass
`/project-assets/`.

## 6. Environment variables

The following variables are required or expected:

```text
PORTFOLIO_PASSWORD_HASH   # preferred password hash
SESSION_SECRET             # random secret, at least 32 characters
AUTH_VERSION               # session invalidation version, usually 1
BLOB_READ_WRITE_TOKEN      # optional direct Vercel Blob token
VERCEL_OIDC_TOKEN          # local Vercel-connected development/upload auth
```

Keep these variables in local `.env.local` or Vercel Environment Variables.
Never commit their values. `BLOB_READ_WRITE_TOKEN` and OIDC credentials must
remain server-only.

## 7. Vercel deployment arrangement

The repository is linked locally to the Vercel project named
`kingsley-portfolio`; the local link is recorded in `.vercel/project.json`.

The intended deployment arrangement is:

1. Keep the GitHub repository private.
2. Import/connect the repository to Vercel.
3. Add the authentication variables to Preview and Production environments.
4. Connect a Private Vercel Blob store.
5. Upload or synchronize project media with `pnpm assets:upload-all`.
6. Deploy a Preview and test protected pages and direct asset URLs.
7. Attach `yuhuiqi.com` after the Preview checks pass.
8. Disable any old GitHub Pages deployment that could expose legacy HTML.

Git integration deploys committed and pushed code. Local uncommitted page
rebuilds do not change the deployed version unless they are explicitly
deployed by another method.

## 8. Reconnection checklist after a page rebuild

Before committing a new page architecture:

- Restore every project that should exist in `projects.data.json`.
- Verify every `source` path exists in the chosen public or private content
  directory.
- Decide where protected HTML lives; do not silently fall back to public HTML.
- Restore the password-entry page and connect its form to the server `POST`
  route.
- Confirm every protected media URL uses `/project-assets/<slug>/...`.
- Confirm protected project media is present in Private Blob under the key shape
  expected by the asset route.
- Confirm public build output does not contain protected HTML or project-only
  media.
- Run `pnpm test:security`.
- Test an unauthenticated page request, wrong password, correct password,
  cross-project session reuse, direct asset access, and cache headers.

The core authentication mechanism should remain independent from the visual
HTML/CSS rebuild. Only the route source lookup, project configuration, password
page markup, and asset URL mapping should need reconnection.

## 9. Security boundary

This system is access control for portfolio presentation, not a substitute for
high-security document distribution. Once an authorized visitor can view a
project, they can still take screenshots, save rendered media, or inspect the
content available to their browser.

The actual protection boundary is server-side page delivery, signed session
validation, private asset delivery, and no-store response headers. Client-side
save deterrence or disabled browser interactions are only supplemental UX
behavior and must never be treated as authentication.
